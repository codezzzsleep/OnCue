# 原生0.4开发版验收

本清单描述应验证的操作，不是通过报告。固定宿主为OctoSense
`6c4746f0854b74446f854fdcd32eeb87b5192a81`、Rinx
`c515e5fc9b6dc22e67f7d551b09fdd793ec685a1`（**官方最新 main，无需任何本地补丁**；
room 控件消歧由上游 PR #48 `bb2a4d4` 提供）、octos
`fe08d8e6b3b32e672b0f956a2b692c3c8205b167`，实测平台为Linux aarch64。

## 导入与布局

1. 从main的实际提交获取bundle，记录版本和摘要。在Rinx自己的Developer入口Review并Run，真实消息用本人授权的私有测试房间。Shell App Hub里的首帧不能替代此实例的Matrix/Octos服务验证。
2. 同时在约990×613模块窗口与更矮的Rinx Developer视口验证，不依赖最大化：现场消息在左，草稿输入、六个保存/取回按钮、路线和播放按钮在右且始终可点；只有末尾只读预览切换对白或A/B。核对两侧滚动区都留下可读高度，消息和假设对白不能只出现一条空白窄带。反复切换预览、滚动消息和对白，不应改变按钮的位置或输入内容。
3. 点击样例舞台、试映下一幕。切换A/B/C，核对三个标题、假设标签、原消息编号和建议台词。样例预设不能记为真实模型结果。

## 播放与改写

4. 选A、播放：逐行出现，按钮变为暂停；暂停后等待超过两个播放间隔，不再推进。下一句只推进一行。重播回到未展开状态，再播放从第一行开始。
5. 播放途中切换B，等待旧计时器原定触发时刻，B不能被旧A回调推进。播放途中切到A/B对照，播放应暂停；从对照点击播放/下一句/重播应回到路线对白。
6. 播放途中修改左侧台词：三路线与旧播放清空。重新试映后，旧计时器/模型回调不能改变新路线。分别试原样例开场、12点后当天回的改法和旅行盲盒玩法。

## 草稿与两版

7. 选择路线后点用这句，将建议放入常驻草稿框，使用键盘编辑并保留这句；清空编辑框再取回，逐字一致。记录实际存储文件和回读结果，不能只看成功提示。先点空档取A也应出现明确提示，区分事件没有送达与文件读写失败。
8. 输入不同文本分别存A、存B。两个版本都显示；取A/取B各自恢复正确文本，按钮不依赖滚动才能点击。空草稿保存应提示并保留已有版本。
9. 关闭整个小程序实例，再从同一账号重新打开，点击A/B对照；两个版本均可取回、修改、上下对照。此处保存的是草稿文本，不宣称保存了完整模型剧本或所有来源消息。

## 真实服务与失败

10. 从附加的本人测试房间载入最近12条文本消息，核对房间和脱密API事件。截完整原生窗口，图上不含凭据。不向真实他人群发送测试消息。
11. 在宿主配置已授权模型，使用同一共享Octos核心完成原生真实模型回合。留存原生结果、宿主服务成功记录与共享连接证据；Python或浏览器MiniMax成功不能代替。处理七块输出、空块/格式不符与provider不可用时的实际反馈。
12. 请求等待期间点停止等待，再重新请求；旧回复不得覆盖新结果。实测90秒期限及连续请求隔离。未附加房间、空房间、模型错误和保存错误都应有清楚反馈，不能假装成功或静默改成样例。
