## 2. 最重要的发现

### OnCue 已经做得好的地方

1. **模型确实进入真实用户路径。** 授权房间读取→实际宿主模型生成→三路线→用户编辑→本地草稿，已有同源码哈希的历史运行记录。部分其他项目实际仍是规则工具、演示数据或固定回放；联网和“Agent”命名不能代替模型作用。
2. **事实显示与模型生成有明确分工。** 相关原文由代码按编号提取，不把模型改写当摘要事实。这与 BuWei 的“模型选事实 ID、代码渲染事实”方向一致。
3. **异步保护是实质优势。** 共享 90 秒期限、一次带原因重试、revision 丢弃旧回调，优于部分仅复位 busy 或回调读取当前选择对象的实现。
4. **本地保存确有回读。** 不把 fs.write 返回成功直接说成已验证；草稿空白不覆盖、A/B 恢复已有测试。
5. **权限范围与产品意图一致。** 不提供发送，避免把假设对白变成对外承诺。真实群聊及宿主模型依赖没有被隐藏。
6. **验证范围较清楚。** 逻辑、工具、实机分别说明，窄屏未判定和模型失败保留。这值得保留，但还不能证明用户价值和语义正确性。

### 相比有参考价值的项目，OnCue 的主要差距

1. **产物持续性不足。** 当前保存的是三份文本，不保存“我想达到什么、用了哪批群聊、选了哪种表达、改了什么”。下一次进入很难继续同一任务。
2. **用户控制模型前提的入口不足。** 有“我想说”，缺“我想达成什么／不要替我做什么”的明确选择；三方向固定，不一定命中拒绝、澄清、催办等具体需求。
3. **差异与依据不够就近。** 相关原文与对白分面板，三条建议要切换阅读；A/B 是取回文本，不是修改前后对照。逐句播放有特色，但不应成为快速选句的必经路径。
4. **语义检查仍弱。** 裸数字全局出现性、中文数字遗漏、固定承诺词和过宽问句豁免都是真限制。原文存在不代表支持模型结论，增加更多黑名单不能解决这一层。
5. **隐私生命周期未完整。** 草稿按账号但不按房间隔离，没有应用内删除。若增加历史，应同时增加保留范围、删除与防恢复策略，不能先收集再补隐私。
6. **没有证明比直接问助手更好。** 十次真实试映测的是能否得到合规输出，未评价是否识别冲突、是否少改几次、用户是否愿意采用、是否省时间。

## 4. 建议的产品方向

保留名称与“先试着说，再决定要不要发”。把用户任务明确为：

> **在存在分歧或需要斟酌的群聊里，形成一份有原文依据、符合本人目标、可以继续修改的待发送草稿。**

不预测具体群友会如何反应、不代发、不承诺达成共识。产品结果是“用户认可的本地草稿与待确认事项”，不是“群聊沟通成功”。

建议体验：**写台词与目标 → 选择本次参考消息 → 三种不同做法及相关原文 → 选一种并提一次修改要求 → 对照前后并保存 → 群聊更新后检查是否需要重新排练。**

逐句假设对白保留为可展开的演示与思考辅助；默认先看到三句建议及每条的“用到的原文／还要问什么”，避免看完动画才能选句。

### 模型与程序的职责

| 模型负责 | 程序负责 | 用户负责 |
|---|---|---|
| 理解表达目标，提出三种做法；识别需要澄清的一处歧义；按新约束修订所选建议；选择相关消息 ID。 | 读授权快照；限制候选 ID；原文原样显示；版本/状态/大小/期限校验；保存、回读、删除；展示变更；应用不申请或调用 Matrix 发送服务。 | 选择消息范围与目标；确认是否将内容交给宿主模型；判断假设是否合适；接受修改并保存。 |

不把一个更长提示词称为多步骤 Agent。只有“读当前证据→必要时询问→生成候选→检查失败后修订→由人应用到同一草稿”真的接通并有证据，才在演示中说明这段任务自动化。

## 5. 实施范围与冻结切线

**推荐本次批准的实现切线**：房间绑定的 A/B 草稿记录＋三建议速览／前后对照＋明确检查状态＋同版本价值与失败场景验证。先保留现有七段生成协议与三种路线，不增加新模型端点、不新增发送权限。

以下完整方向分成这条切线与后续扩展。不是所有研究启发都要在本次冻结前完成。

### 主要成果：可继续修改的私人排练记录

围绕当前 A/B 结构，不引入任务平台：

- 每次生成保有本地 `rehearsal_id`、房间身份、台词、来源快照标识与结果 revision。冻结切线只持久化本房间最近的 A/B 草稿和必要的生成元数据，不默认保存全部对白或聊天历史。
- 原文区沿用当前 1–4 条编号摘录。三建议直接速览，选择仅放入编辑框；保存仍是独立动作。
- 用简洁前后对照显示“选中的助手建议／用户修改后的草稿”，保持现有 A/B 槽位及取回按钮，不要求逐字彩色 diff。
- 同一记录修改/重新生成后增加 revision；旧候选可查看，但不能冒充新上下文检查通过的结果。未通过校验显示原因类别和恢复动作，不把规则文本标成助手结果。

验收：用户可直接比较三句并编辑；改台词/换来源/停止后旧回调不能更新候选；应用与保存对象、文本、revision 一致；重开仍取回所属房间草稿；失败不覆原稿。

绑定必须从生成或载入开始：候选与编辑器分别拥有房间/快照/text_revision，不能在保存时把当前房间贴到旧文本上。手改、取回 A/B、换样例、换房间、删除均更新对应状态并使旧应用资格失效；删除同时取消在途本地回调。未取得真实 room_id 时只允许会话内手工编辑，不用房间名降级隔离。来源标识使用不可变快照内容，不把重载后的 #2 当作旧依据；本次不落盘引用正文，重开后显示来源待载入。

**不放进本次冻结切线的协议扩展**：表达目标、最多一轮澄清、针对所选路线的模型修订、逐路线来源结构与选消息发送。当前生成器固定七节，建议强制含问号，不天然支持礼貌拒绝陈述句或单路线修订响应。扩展前需单独设计并版本化协议、确定字段与缺省值、重跑 parser/grounding/retry/存储和真实模型多场景评测；不能只加输入框或放宽校验就声称实现。完整产品方向保留在第4节，待本次切线通过再审阅。

### 支撑 A：房间隔离、删除与安全恢复

- 用宿主真实房间 ID 做记录边界，不用房间名。账号隔离继续依赖宿主，不新增读取账号的权限。
- 三份旧文本（主草稿、A、B）统一进入“旧版未分组”入口；启动不自动展示正文或认领当前房间。导入明确为复制，旧副本保留并有单独删除入口；删除本房间草稿不隐含删除旧版副本。
- 新结构包含 schema version、草稿 revision、来源取得时间与来源快照标识。本次只保存草稿与必要元数据，原文引用只在当前会话展示；不默认把全部消息或模型会话持久化。重新打开后标“来源待重新载入”，没有原文就不假装完成复核。
- 最小结构为 `{schema:1, revision, rooms:[{room_id, draft, take_a, take_b}]}`；每槽记录 text、text_revision、origin（manual/model）、可选 rehearsal_id、snapshot_id、generated_at，字段类型严格校验。最多10个房间，每槽最多8000 UTF-8字节，记录文件最多512 KiB；超限停写并提示清理，不静默淘汰，不把房间 ID 拼成文件路径。
- 整份新状态写后回读成功才提交内存状态；A/B 是用户稿件版本，不是故障备份。是否需要额外恢复副本、崩溃中写入的恢复策略须在存储实现时验证；不把现有文本回读等同原子事务或失败后磁盘一定未变。
- 显式“删除本房间草稿”列明将移除的新结构记录和应用保有的恢复副本；从结构化文件移除相应字段并回读确认、重开不复活，即为逻辑删除。对单独遗留文件需核实宿主实际删除能力；不能把清空输入框、隐藏列表或空白内容覆盖当成已删除。不得宣称存储介质安全擦除。
- 删除后重开不能从备份复活。第三方模型或宿主日志的保留由宿主决定，应用不能声称同步擦除。
- 加载到未知 schema 或损坏文件时保留原数据并停写，不能静默恢复默认覆盖。

验收：两房间不串草稿；同名不同房间仍隔离；旧版迁移可拒绝；保存失败保留编辑内容；删除重开无残留可恢复记录；未授权房间不能被自动载入。

### 支撑 B：检查状态与数据范围更明确

- 本次先沿用现有校验协议；显示格式／引用／数字／承诺类别，区分助手候选和用户编辑。用户编辑不因未通过模型候选规则被禁止保存，也不继承“检查通过”状态。
- 固定说明“相关原文由程序取出，三种说法是助手假设”。原文包含数字不证明生成语义正确，界面不显示“事实验证通过”。
- 显示本次应用 payload 的实际消息条数和远程模型提示。沿用全部已载入消息的当前范围，不提前宣称支持消息选择或匿名化。
- 模型失败、用户不愿传递上下文时，仍能查看已载入原文和手工编辑；不会伪造“模型已理解”。

单独列为协议扩展：逐路线来源范围、数字类型/单位、中文数词、问句豁免收紧、消息选择与姓名匿名化。这些改动需要独立负例与合法例，不同功能之间不混改；只有证明旧功能未退化才纳入发布。

本次验收：检查类别与真实拒绝原因一致；手工编辑正确撤销候选检查标记；实际 payload 与界面说明一致；失败保留原草稿。对既有语义盲区仅准确披露，不承诺本次已补齐。

### 实现前必须核实的宿主契约

1. **session.open 是否新建独立历史。** 当前应用每次调用它，但本地 broker 的 `ensure_bound` 可复用 session，`ContextOp::Open` 仅回报已打开。不能凭服务名断言每次没有历史；也不能把本地源码直接等同目标二进制。必须用隔离合成输入核实，未证实前不宣称缩小消息范围或删除草稿能移除模型先前上下文。
2. **宿主工具权限。** 应用不申请／调用 Matrix 发送；提示词要求不使用工具只是文字约束。宿主工具由宿主配置，未核实其禁用策略前，不保证模型没有任何外部副作用。不得用未支持的 `tools`、session ID 等参数绕过宿主。
3. **输入预算与取消。** 本地 Rinx `octos.turn.start` 只接收 text，限 32 KiB；未来带原稿、修订要求和引用时须按 UTF-8 字节预检。停止保证本地旧结果不生效，不承诺远端退费、撤回或清历史。

这三项用于确定真实数据/授权边界；验证未通过时，缩减对应功能与文案，不自行修改宿主。

本地 Rinx 源码显示 `matrix.room_info` 可返回 room_id，消息可带 event_id/ts；当前 OnCue 只取房间名，将整批消息留在内存并放入试映请求，磁盘仅保存草稿文本。**本地源码不是当前运行二进制的能力证明**：实现前需在隔离宿主核实返回形状；缺字段时标“当前快照”，不能把 #2 这样的窗口序号当稳定事件 ID。

刷新最近 12 条仅能判断“窗口内容变了”，不能断言某条消息已删除或被撤回，也不是关闭应用后的持续监听。新证据出现时保留旧草稿、标记需复核，不直接把旧稿清掉或让模型覆盖。

建议内部时间门槛：10月8日晚完成获批最小链路，10月9日中午锁功能，余下时间仅修阻断问题、重跑验证、队外试用和录屏。房间/删除宿主能力无法确认时，不发布新增来源持久化，保留速览/对照与现有存储边界并如实标注限制。

如果最小链路无法在冻结前完整实现并重测，使用已验证基线或已独立完成验证的更小改动，不拼接半成品能力；任何应用内容改动都要新版本。用户确认范围后再实施，本研究不提前改协议或增加权限。

## 6. 必须增加的价值与可靠性证据

### 三个固定场景，而非单一旅游例子

1. **时间/预算冲突**：群聊有中午才能出发、当天返回，台词却提早出发住一晚。
2. **礼貌拒绝与边界**：拒绝承担某件事，但不替他人答应、不凭空承诺替代方案。
3. **催办与澄清**：推动明确责任或截止时间，不能把“待确认”写成“已经完成”。

最低证据：至少一名队外用户，在三个获准或合成场景上，对候选复赛版与同一宿主模型的直接问答作成对比较。交替先后顺序，记录原始输入、首次可用时间、调用/重试次数、用户修改量、冲突识别、无依据承诺及最终选择，说明是否更容易选句或更符合目标。手工编辑和0.4.8额外对照有余力再补，不挤占最终验收。

记录反馈和拒用原因；少量样本只报告观察，不给普遍准确率，不宣称已证明 PMF。没有队外试用就写未验证。

### 分层测试

- Python 工具测试与 VM 应用逻辑继续分开，不把 CI 绿灯作为应用通过。
- 新状态需要真实生产函数路径的用例：来源/目标/房间变化、旧回调、重复应用、保存失败、重启、删除、迁移、过期结果仍可读但不可静默套用。
- 保留本次请求 90 秒共享期限，修订失败不覆原稿；校验拒绝按格式/引用/数字/承诺/服务错误分类，才能区分合理拒绝与误拒。
- 窄屏播放验收不依赖“随机剩余两行”的时机，使用隔离的可控对白测定时器，另做真实模型路线的正常交互验收；两类结果分别记录。
- 所有发布证据绑定最终 bundle 源码哈希和宿主版本。不可将旧版模型成功、新版UI成功、另一个宿主存储成功拼成一条完整成功链。

改应用包后仍按 [仓库约定](../../AGENTS.md) 升版、工具测试、八套 VM 逻辑测试、更新验证哈希与更新记录。作者负责盖章/签名、标签、推送、发布和最终录屏；这轮研究未做这些动作。
