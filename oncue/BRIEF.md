# OnCue · 群聊试映室：产品说明

## 用户任务

在群聊存在分歧、需要拒绝或推动下一步时，先私下比较几种表达，再形成符合本人目标的草稿。OnCue 不预测具体群友反应，不替人同意，也不发送消息。

## 使用过程

1. 载入已授权房间，展开原文列表，勾选本次需要参考的消息。消息最多12条，保留原来的编号。
2. 写台词，选择澄清条件、礼貌拒绝或推动下一步，必要时补充边界。
3. 单独允许当前房间/消息范围内的模型请求；点击试映生成三种不同表达，原文与助手假设分开显示。
4. 直接速览三句建议，选一条进入编辑框。假设对白可另行逐句播放，不是选择建议的必经步骤。
5. 手工修改，或提出一条修订要求。助手修订先进入候选区，展示原稿、候选、依据及改动说明；用户明确应用后才改变草稿。
6. 对照原稿/当前稿，或比较已保存A/B。保存与应用分开，保存完成需核对实际写入。
7. 重新打开并载入同一房间后恢复主稿，可另行取回A/B。旧稿带有本地来源标记，需人工对照新载入的原文；不提供跨会话自动变更检测。

样例舞台完全在本地运行。三种表达按目标选择规则模板；修订是固定交互样例，不冒充模型理解修改要求。

## 持久化与恢复

账号范围由宿主管理，应用用稳定房间ID隔离主稿/A/B；样例独立保存。旧版三份文本仅在用户明确选择时复制，不自动归属房间。删除新房间记录与旧版文件分别确认。

记录保存目标、台词、所选原稿、来源编号/快照标识、时间与文本版本，不保存整批聊天正文。最多10个房间、每稿8000 UTF-8字节、文件512 KiB。损坏或未知格式锁定写入，编辑内容仍可保留；不自动覆盖为空数据。只支持一个写入窗口，无跨进程锁和崩溃原子性保证。

## 模型与程序分工

模型理解表达目标、提出不同候选并按明确要求修订。程序控制来源、请求身份、格式/引用/数字/承诺规则、期限、候选应用与存储。用户判断语义是否符合原文及本人意图。

生成协议G2保留七节：`【摘要】`、`【A对白】`、`【A建议】`、`【B对白】`、`【B建议】`、`【C对白】`、`【C建议】`。每路线有两个虚构回应、一行包含1–4个来源ID的依据和待确认点；建议一行150字以内，允许拒绝陈述句。

修订协议R1为 `【R1依据】`、`【R1建议】`、`【R1说明】`。候选绑定原稿实际文本、文本版本、房间、来源、目标和修改要求，应用一次后即消费。两类请求共享各自90秒总期限，最多修复一次，完整请求最多32 KiB。

引用正确不代表语义支持；数字校验是有限的字面约束，不是完整事实验证。手工编辑不继承候选检查状态。详细数据范围见[数据说明](PRIVACY.md)。

## 能力

| 能力 | 用途 |
|---|---|
| `storage` | 房间草稿、A/B、迁移、回读和删除 |
| `matrix.room_info` | 房间名称及稳定身份 |
| `matrix.read_messages` | 读取授权房间最近文本 |
| `octos.session.open` | 请求打开宿主助手上下文 |
| `octos.turn.start` | 生成三路线或修订一个草稿 |
| `octos.turn.interrupt` | 请求中断；本地旧回调同时失效 |

不新增联网、发送、日历、相机或定位权限。宿主控制模型工具与历史，应用不承诺打开会话即清空历史。
