## 一、最关键的一条：我们属于「原生宿主扩展」形态

`rinx-miniapps.md` 明确：
> 当前原生加载**只接受内置文章编辑器的准确 ID、版本与摘要**；**没有通用远程应用市场、任意脚本导入或发布者签名验证**。
> **扩展其他原生应用需要修改宿主。**
> **网页卡片不提供 Matrix 登录令牌、聊天记录或原生能力桥。**
> 新增原生应用需**在自己的宿主分支中扩展并构建**，提交**完整源码、宿主提交号与启动方式**，
> **不能只交任意 `.card` 文件并假设现有宿主会安装。**

`app-hub-submission.md` 的形态表：
| 形态 | 交付方式 |
| --- | --- |
| Hub 卡片包 | manifest/listing/page.card/kit + 预检 + 实际运行证据 |
| 网页小程序 | 源码 + 可运行页面 + URL 卡片 + 部署说明 |
| **原生宿主扩展** | **含扩展的可构建宿主版本、源码提交号、支持平台与运行说明** ← 我们 |

**⇒ 我们的交付必须包含「打过补丁的 Rinx 宿主」本身**（fixed 0879548 + local lookup patch），
而不是只交 `oncue/bundle`。`deploy/DEPENDENCIES.md` 已钉 `0879548ba826c786eb6ad3f60dfba7bd342bd750`，可作起点。

## 三、**我们完全没有的一项（官方明确要求）**

> 实际演示应覆盖启动、真实输入、必要授权、Agent 执行、结果核验和失败处理。
> **聊天或账号相关作品还需演示「接收者独立授权」，避免把发送者身份或权限带给接收者。**

我们**没有任何接收者独立授权的证据**（`grep 接收者/独立授权` 在 README/oncue/evidence 下无命中）。
Rinx 基线文档也把这条列为核心机制：「每次打开须授权；授权关联账号、登录会话和应用实例，最长一小时，
关闭或退出后撤销」「分享应用入口，接收者使用自己的账号与草稿」「不能继承发送者的权限」。

⇒ **需要两个账号的独立授权演示**（发送者分享卡片 → 接收者打开并独立授权 → 得到自己的授权与草稿、
不继承发送者权限）。这是**目前最明确的未交付项**。

## 四、官方推荐的预检命令（我们可直接跑）

```sh
hub stamp my-app
hub check my-app --allow-unsigned
hub scan my-app --packet review.json
```
`--allow-unsigned` 仅用于本地预检，不代表正式发布。**我们当前包即为未签名，正好适用**。

## 五、赛事自带的 Rinx Matrix 服务与我们当前环境不同

`rinx-guide.md`：注册与登录 `https://auth.matrix.rinx.chat`，Homeserver `https://matrix.rinx.chat`，
完整账号 `@{user}:matrix.rinx.chat`，统一认证（SSO），初始显示名可能带 `⚡`。
**我们当前用的是 `@codezzzsleep:matrix.org`。** 若评审按赛事基线复现，需要确认是否应改用
`matrix.rinx.chat`；这一点需要 HUMAN/主办方确认（属账号与外部服务范畴）。

## 六、建议的补法（按优先级）

1. **接收者独立授权演示**（官方硬要求，我们缺）——需第二个账号；
2. 交付形态改标为**原生宿主扩展**：附可构建宿主（补丁）+ 宿主提交号 + 启动说明 + 支持平台；
3. 打 tag/写明固定提交号 + 在 README 顶部给出「评审复现路径」；
4. 跑 `hub check --allow-unsigned` 与 `hub scan`，把输出入库；
5. （可选）录一段运行视频。
